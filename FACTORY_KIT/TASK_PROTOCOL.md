# TASK PROTOCOL — 任务与消息协议

## 为什么需要协议

多智能体协作的默认失败状态不是"吵起来"，而是"**安静地互相错开**"：
每个人都在忙，都觉得自己做完了，最后拼不起来。

协议的作用是让「做完了」这件事**有据可查**。

---

## 消息模板（≤ 1KB）

每次交付/汇报都必须是这个结构：

```
任务ID：T02
状态：DONE / BLOCKED / NEEDS_REVIEW
修改路径：（所有写过的文件，一行一个）
核验命令及结果：（真实命令 + 真实数字，不是"已测试"）
风险：（一个最高风险，没有就写"无"）
下一步：（一条具体建议）
```

### 为什么强制"核验命令及结果"

没有这一栏，`DONE` 就只是一个词。

**反例**：
> 任务ID：T02 / 状态：DONE / 算法单测已完成 / 下一步：继续

**正例**：
> 任务ID：T02 / 状态：DONE
> 修改路径：tests/core/core.test.mjs, tests/core/README.md
> 核验命令及结果：`node --test tests/core/*.test.mjs` → 45 pass / 0 fail / exit 0
> 风险：性能断言依赖机器，CI 抢占时可能假阳性
> 下一步：可接新用例

第二条让 Lead 能**立刻复现**你的结论。第一条只能让 Lead 相信你。

### 为什么不要贴大段日志

- 消息通道有上限（本项目约 64KB），日志会挤掉有用信息
- Lead 需要的是**结论 + 复现方式**，不是原始输出
- 日志的正确去处是**文件**，消息里只放路径

**规则：日志进文件，消息里放"命令 + 结果摘要 + 文件路径"。**

## 任务状态机

```
        ┌───────────────────────────────────────┐
        │                                       │
  [pending] ──claim──> [in_progress] ──完成──> [done]
        │                    │
        │                    └──受阻──> [blocked]
        │                                    │
        └──────────── 依赖满足后重新 ready ────┘
```

### 各状态的含义

| 状态 | 含义 | Lead 该做什么 |
|---|---|---|
| `pending` | 已创建，没人认领 | 检查 `ready`（依赖是否满足），分配 owner |
| `in_progress` | 有人在做 | 不要打扰；等消息或定期看文件变化 |
| `done` | 交付完成，**且附了核验命令与结果** | 复核证据，不只看状态 |
| `blocked` | 做不下去 | 看阻塞原因，决定：换人/降级/砍功能 |

### 三个必须知道的坑

**坑 A：消息发送成功 ≠ 任务完成**

`send_message` 返回 `{sent: true}` 只表示消息进了对方的收件箱。
对方可能：还没处理 / 处理到一半 / 睡着了 / 理解错了。

**判据必须是"文件变了 + 核验命令跑过了"**，不是"消息发出去了"。

**坑 B：`inactive` ≠ 失败**

成员空闲（inactive）只表示"当前没有回合在执行"，不是"任务失败"。
它可能刚做完、也可能在等依赖。判断依据是**任务板状态 + 文件时间戳**。

**坑 C：创建失败会占用配额**

本项目遇到 `Team member limit 8 reached` —— 成员创建失败**也计入配额**。
所以：
- 不要为了"试试看"反复创建同名成员
- 创建前先想清楚这个角色是否真的需要
- 角色数量是**容量**，不是成功指标

## 依赖怎么表达（DAG）

不要靠"我等下再问你"，要用**显式的依赖关系**：

```
T00 (环境自检) ──────────────────────┐
                                      ├──> 所有任务
T01 (PRD/验收标准) ──┬──> T04 (视觉)  │
                     └──> T05 (UI)    │
T02 (算法接口+单测) ─┬──> T05         │
                     └──> T07 (QA)    │
T05 (UI 闭环) ──────────> T07         │
T06 (示例/叙事) ────────> T07         │
T07 (QA) ─┐                          │
T08 (红队) ─┴──> T09 (发布)           │
T10 (素材) ──────────> T11 (最终交付) ┘
```

### 本次项目的真实依赖

| 任务 | 依赖 | 为什么 |
|---|---|---|
| T05 UI | T01（PRD）、T02（算法接口） | 没有接口就无法调用；没有验收标准就不知道做成什么样 |
| T07 QA | T05、T06 | 没东西可测 |
| T09 发布 | T07、T08 | 没过 QA 和红队不许公开 |
| T11 最终交付 | 全部 | — |

### 依赖的实践规则

1. **只有真依赖才连边**。T03（竞品调研）不依赖 T01，可以并行，别为了"整齐"乱连。
2. **被依赖的任务，产出必须是"可用的接口"，不是"完美的实现"**。
   例如 T02 的产出是 `core.mjs` 的**函数签名 + 能跑**，不是"所有边界都覆盖"。
   后者可以后补，但不能挡住 UI 开工。
3. **关键路径上的任务，Lead 要亲自盯**。本次关键路径是：
   `T02 算法 → T05 UI → T07 QA → T09 发布`。这四件事任何一个卡住，整个项目卡住。

## 并行度控制

**不要一次开满。** 本次项目的节奏：

| 阶段 | 活跃成员 | 理由 |
|---|---|---|
| 启动（0-30min） | 2（product-owner + logic-engineer） | **试运行**，验证工具链是否真的可用 |
| 早期（30-90min） | 3-4（+ ux-writer, story-engineer） | 接口已定，可以并行 |
| 中期（90-180min） | 4-5（+ qa-engineer, growth-producer） | — |
| 后期 | 2-3（qa + release + Lead） | 其他停止新任务，避免改动未测代码 |

**为什么先 2 个**：如果团队工具本身有问题（配额、消息、任务板），
在 2 个成员时发现，代价是 2 份工作；在 8 个成员时发现，代价是 8 份。

本次试运行确实是必要的：product-owner 和 logic-engineer 在第一小时内就各自发现了
`core.mjs` 的真实 bug —— 这证明了"多读一写 + 独立复算"的模式可行，之后才敢扩到 8 人。

## 失败处理

### 成员卡住

1. 看 `list_agents`（是在跑还是空闲）、任务板 owner、**最近文件修改时间**
2. 发一条简短消息问一次（不要连环追问）
3. 必要时 `interrupt_agent` 中断其当前回合
4. **中断不会自动释放任务** —— Lead 必须手动查任务板并重分配
5. 重分配前**先看工作树**，防止两个成员同时改同一个文件

### 成员产出不合格

不要直接改它的文件（会破坏写入区约定）。做法：

1. 指出具体哪一条不满足验收标准（引用文件路径和行号）
2. 让它自己改
3. 如果时间不够，Lead 接管**并明确记录接管**（改了什么、为什么）

### 工具失败

**同一个工具失败 2 次，立刻换路径**，不要重试第 3 次。

本次项目的真实例子：
- `node --test tests/` 失败 → 第 1 次怀疑代码 → 第 2 次确认是命令用法 → 换 `node --test` → 成功
- Team member limit 8 → 不重试，改为 Lead 自己写 FACTORY_KIT

## 检查点（每 30-45 分钟）

```markdown
# CHECKPOINT
北京时间：
当前项目路径：
已验证的最近 commit：
最新运行命令/结果：
当前站点和发布状态（真实链接或 NOT_PUBLISHED）：
已经完成的 3 项：
未完成的 3 项：
下一次可行动的第一步：
谁在做什么（owner/task ID）：
费用与认证状态：
硬截止：
```

**为什么是 3 项**：写 10 项就会开始写流水账，写 3 项才能逼出"真正重要的"。

**检查点的真正用途**：让下一个 Lead 在 **5 分钟内**接手。
所以"下一次可行动的第一步"必须是**具体动作**（"跑 node --test，然后建仓库"），
不是"继续推进"。
