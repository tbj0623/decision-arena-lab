# FAILURE_LIBRARY — 失败案例库

> 这里记录本项目真实踩过的坑。**不是教你怎么写对，是记录我们怎么写错的。**
>
> 写这份文档的理由：今晚的 10 个坑里，有 7 个是「测试全绿但仍会炸」。
> 如果每次都记成"测试没覆盖"，那说明问题不在测试覆盖率，而在**测试策略本身**。
> 所以每条都诚实填了「为什么测试没抓到」这一栏。
>
> 整理时间：2026-10-29 · 分支 `night-v8`

---

## 阅读方式

每条按固定五段：**症状 → 根因 → 为什么测试没抓到 → 怎么修的 → 以后怎么防**。

第三栏是这份文档的价值所在。如果一栏只写"测试没覆盖"，等于什么都没说。
所以每条都追到了**具体的测试盲区类型**，末尾有归纳。

### F-01 · 审计脚本「绿色但可绕过」——7 类混淆写法全部逃过

**症状**
`node scripts/check-no-network.mjs` 输出 `PASS：未发现网络请求`，
但页面里确实有 `fetch()` 在往外发请求。CI 全绿，隐私承诺已经是假的。

**根因**
审计脚本早期是**逐行正则匹配**，只认字面量 `fetch(`。
攻击者（其实是 red-team 同学）用 7 种写法绕过去：

| 绕过手法 | 例子 |
|---|---|
| 大小写混用 | `FETCH(` |
| 字符串拼接 | `fe` + `tch(` |
| 方括号取属性 | `window['fetch'](` |
| base64 隐藏 | `atob('ZmV0Y2go...')` |
| fromCharCode | `String.fromCharCode(102,101,116,99,104)` |
| 跨行拆分 | `fe\n tch(` |
| 注释夹在中间 | `fe/*x*/tch(` |

**为什么测试没抓到**
测试只验证了「**应该检出的东西被检出**」，没有验证「**故意伪装的写法是否也被检出**」。
这是安全类测试最典型的盲区：开发者会不自觉地只写"正常输入"用例，
因为写正常用例时脑子里想的是"功能对不对"，而不是"攻击者会怎么绕"。

更隐蔽的是：审计脚本**自己**也产出了 PASS，产生了一种"已验证"的错觉。
一个只会说 PASS 的检查器，和一个永远返回 true 的函数没有区别。

**怎么修的**
从"匹配字面量"改成"归一化后匹配"：先剥注释、拼字符串、解 base64、
还原 `String.fromCharCode`，再做匹配。并补了 5 条绕过回归测试
（`tests/qa/audit-script.test.mjs` L156-187），其中「审计-绕过4：注释豁免不能被用来藏真实代码」
是最关键的一条——它防止了"免规则"被反向利用。

**以后怎么防**
写完任何"检查器"，**立刻为它写 3 条「故意绕过」的用例**。
检查器的测试用例里如果没有一条是攻击视角的，它就不是安全工具，是安慰剂。

### F-02 · `gate.mjs` 的 `release-freshness` 门是「假通过」

**症状**
`dist/` 里明明躺着 `demo.zip`，跑门禁却输出：

```text
✅ 发行包比源码新     dist/ 无 zip，跳过
```

绿灯。但这个"跳过"是假的——它其实读目录失败了。

**根因**
两处叠加，单独看都不致命：

```js
function readdirSafe(d) {
  const { readdirSync } = require('node:fs');   // ① ESM 里没有 require
  return readdirSync(d);
}

let zips = [];
try {
  zips = readdirSafe(distDir).filter((f) => f.endsWith('.zip'));
} catch { /* ignore */ }                        // ② 异常被静默吞掉
if (!zips.length) return { pass: true, detail: 'dist/ 无 zip，跳过' };
```

① `gate.mjs` 是 ES Module，`require` 未定义，调用必然抛 `ReferenceError`。
② 调用处用 `catch {}` 把异常吃掉了，`zips` 永远是 `[]`。
③ 于是永远走 `pass: true` 的"无 zip，跳过"分支。

**为什么测试没抓到**
这不是"测试没覆盖"，而是**测试压根测不出来**：

- 门禁在"没有 dist/ 的干净仓库"里跑，`existsSync(distDir)` 为 false，直接提前返回，
  **代码根本走不到出错那一行**。
- 只有在"恰好有 dist/ 且里面有 zip"时才会触发。而正常开发时 `dist/` 是 gitignore 的，
  本机经常没有，所以这个分支长期不被执行。
- 更根本的问题：**没有测试断言"跳过必须是可确证的"**。
  `pass: true` 有两条路径——"确认没有"和"读失败"，但代码把它们合并成了同一个结果。

**怎么修的**
改用顶部已 import 的 `readdirSync`；并且把语义分开：

```js
let zips;
try {
  zips = readdirSync(distDir).filter((f) => f.endsWith('.zip'));
} catch (e) {
  return { pass: false, detail: `无法读取 dist/：${e.message}` };  // 读失败 = 门失败
}
if (!zips.length) return { pass: true, detail: 'dist/ 存在但无 zip，跳过' };
```

修完后实测：`dist/old.zip`（mtime 3 小时前）→ `⚠️ 过期：old.zip`；
zip 比源码新 → `✅ 1 个 zip 均比源码新`。

**以后怎么防**
**任何 `catch {}` 后面接 `return pass:true` 的地方，都要当成 bug 审。**
"跳过"只能用于**能明确证明的正常情况**（比如目录确实不存在），
读取失败、解析失败、超时一律算失败。宁可误报，不可假通过。

### F-03 · 用 `todo` 掩盖真实缺陷——"fail 0 在撒谎"

**症状**
`node --test` 输出：

```text
ℹ tests 92
ℹ pass 86
ℹ fail 0
ℹ todo 5
```

CI 全绿（`fail 0`），但产品有 5 个已知问题没修，其中一个是
**首屏文案写着「默认的六个因素」，而实际只有 4 个** —— 用户一眼就能看见。
这个错误从开发到"发布完成"一直存在。

**根因**
Node 的 `todo` 测试**不算失败**。`fail 0` 只统计真正的失败，
`todo` 是"我知道它没实现，先记着"。于是在"只看 fail 数"的视角下，
todo 变成了一个**合法的隐藏区**。

问题在于：`todo` 本该用于"设计上待定的行为"，
但我们把它用成了"已知 bug 的隔离区"。一旦养成习惯，就会不断往里塞。

**为什么测试没抓到**
因为**这些测试本来就被写成了不执行**。它们不是"漏抓"，是被主动标记成了 `todo`。

更深的问题：**CI 只看 `fail` 数**。`todo` 从 5 涨到 50 也不会报警。
指标选错了，等于给了自己一个合法撒谎的通道。

**怎么修的**
- 把 `todo` 一条条转成真断言。那条"六个 vs 四个"的文案断言，转正后立刻变红，
  暴露了首屏事实错误，修完才变绿。
- `gate.mjs` 的 `tests` 门加了硬规则：**`todo > 0` 直接判不通过**：

```js
const ok = f === 0 && p > 0 && t === 0;   // ← todo 必须为 0
```

现在项目是 `176 tests / 176 pass / 0 fail / 0 todo`。

**以后怎么防**
把 `todo` 数量当作**和 fail 同等重要的指标**，而不是它的补充。
如果确实需要 `todo`，那就必须设一个上限（比如 0），否则它一定会变成垃圾场。

### F-04 · 部署漂移——「本地修了」不等于「线上修了」

**症状**
本地测试全绿，`site/app.mjs` 确实改好了。但打开线上站点，
修复**完全没生效**，用户看到的还是旧版。

**根因**
链路上有三个独立的断点，每一个都能单独造成"本地好、线上坏"：

1. **没 push** —— 本地 commit 了但没推。远程 `main` 还停在旧 SHA。
   实测过：本地 `de472bd` vs 远程 `d126d238`，差一个 commit。
2. **push 了但没部署** —— Pages 的 workflow 因为时序问题失败（见下）。
3. **部署了但有缓存** —— GitHub Pages 返回 `Cache-Control: max-age=600`，
   浏览器 10 分钟内继续用旧 `app.mjs`。

第 3 条最阴：明明部署成功了，你打开浏览器一看还是旧的，很容易误判成"部署没生效"，
然后去查日志、重新触发，白折腾一圈。

> 第一次 push 触发的 run 还真的失败过一次：
> `Failed to create deployment (status: 404) ... Ensure GitHub Pages has been enabled`
> 原因是该 run 于 12:03:48 执行 deploy，而 Pages 直到 12:04 才 POST 成功——**时序竞争**。

**为什么测试没抓到**
**本地测试的输入永远是工作区文件，不是线上的字节。**
`node --test` 不知道怎么验证"用户浏览器里跑的是什么"。

即使加了 E2E，如果只测本地起服务器，仍然测不到"线上部署的是哪个 commit"。

**怎么修的**
建立"三方一致性"验证，每一环都要有证据：

```text
① 本地 blob  = git hash-object site/app.mjs
② 远程 blob  = gh api .../contents/site/app.mjs?ref=main --jq .sha
③ 线上字节   = 抓 https://<site>/app.mjs 算 SHA-256
三者必须完全相同
```

验证部署是否生效时，**必须用 CDP 清缓存**：

```js
const client = await page.context().newCDPSession(page);
await client.send('Network.clearBrowserCache');
await client.send('Network.setCacheDisabled', { cacheDisabled: true });
```

**以后怎么防**
发布验证的判定标准不是"我看到页面打开了"，而是"**线上返回的字节哈希 == 仓库里的 blob 哈希**"。
并且验证脚本要带**反向用例**（请求一个不存在的路径，必须 404），否则"全部 200"可能只是 SPA 兜底。

### F-05 · 承诺「双击 `file://` 就能用」，用户看到白屏

**症状**
README 写"下载后双击 `index.html` 即可使用"。用户照做，浏览器打开一片空白，
控制台一行红字：`Access to script at 'file:///...' from origin 'null' has been blocked by CORS policy`。

**根因**
原生 ES Module（`<script type="module">`）在 `file://` 协议下受同源策略限制，
`file://` 的 origin 是 `null`，模块加载被浏览器直接拒绝。
**这不是 bug，是规范行为**，任何现代浏览器都一样。

问题出在文档承诺了一个技术上不成立的用法。

**为什么测试没抓到**
测试是 `node --test` 跑的，**Node 里没有 `file://` 的 CORS 限制**。
`import './core.mjs'` 在 Node 里永远成功，在浏览器 `file://` 下永远失败。

这是**运行环境差异**导致的盲区：测试环境比真实环境宽松，
所以测试通过反而更有欺骗性。

**怎么修的**
文档改成必须走 HTTP（`node scripts/serve.mjs` 或 `python -m http.server`），
并在 README 里明确写"不要双击打开"。

另外加了一道非阻断门禁 `no-file-protocol-claims` 自动检查：
README 里出现 `file://` 时，必须同时出现「打不开 / 不支持 / 必须走 / CORS」这类警告词，
否则报「提及 file:// 但没有警告，可能误导用户」。

**以后怎么防**
凡是"在某环境下能跑"的承诺，都要**在那个环境里验证一次**，不能在更宽松的环境里验证后就宣称成立。
特别是：`file://` vs `http://`、有网 vs 无网、有缓存 vs 无缓存。

### F-06 · `toFixed(1)` 让同一行出现两个精度

**症状**
反转阈值卡片上写着：

> 把「收入确定性」的权重占比降低到 **39.4%**，两边就会打平。

用户照着拖到 39.4%，发现**并没有打平**——两边还差一点点。
同一张卡片下面又显示「精确 39.3939%」，一行之内两个精度，互相矛盾。

**根因**
阈值本身是无理数级别的数（39.393939…%），任何有限位小数都只能"约等于"。
但文案用 `toFixed(1)` 把它说成了确定的 39.4%，而 39.4% 处实测 Δ ≠ 0。

这是个**语义错误伪装成显示错误**：不是"少显示几位"，是"把约等号说成了等号"。

**为什么测试没抓到**
测试断言的是**数值计算正确**（阈值算得对），没有断言**文案与数值是否一致**。
"39.3939 算得对"和"39.4 这句话说得对不对"是两件事，但代码里它们隔得很远：
一个在 `core.mjs` 的纯函数里，一个在 `narrative.mjs` 的字符串拼接里。

**怎么修的**
- `pct()` 增加 `digits` 参数，默认仍是 1 位（保持简洁），但关键处传 2 或 4
- 文案统一改成「**约 X（精确 Y）**」的句式，明确表达"这是近似"
- 滑杆 `step` 改成 `"any"`，让拇指能精确停在真实临界点
  （原来是 `step="0.1"`，导致"跳到精确临界点"按钮只改了数字、拇指没动，
  界面上出现两个互相矛盾的位置指示）

**以后怎么防**
**凡是把浮点数展示给用户的地方，都要问一句"用户会不会照着这个数字去操作"。**
如果是，就必须给出足够精度，或者明确标注是近似值。
测试要断言"文案里的数字与真实值在标注精度内一致"，而不只是"计算正确"。

### F-07 · `!opA.value` 恒为假——初始值不是空字符串

**症状**
一段"输入框为空时才写入默认值"的逻辑，看起来天衣无缝：

```js
if (!opA.value) opA.value = DEFAULT_A;   // 期望：空的时候填默认值
```

但它**从来没有执行过**。输入框里始终是旧内容，用户改了方案名也不会同步。

**根因**
`opA` 的初始值不是 `''`，而是 `"方案 A"`（HTML 里写死的 value）。
所以 `!opA.value` 对非空字符串恒为 `false`，整个分支是死代码。

真正的判断应该是"**当前值是不是占位符**"，而不是"是不是空"：

```js
const isPlaceholder = opA.value === '' || opA.value === DEFAULT_A;
```

**为什么测试没抓到**
因为这段代码**不报错**。它只是安静地不执行。
所有测试都在验证"最终结果对不对"，而初始值恰好是对的（默认文案本来就是"方案 A"），
所以错误的逻辑和正确的逻辑产出了**相同的初始状态**。

只有当用户开始操作、需要"重置回默认"或"判断是否用户输入"时，差异才显现——
而那个场景没人测。

**怎么修的**
把"空"的判断换成"空**或**等于占位符"的显式判断，
并把 `DEFAULT_A` 抽成常量，避免字符串散落各处。

**以后怎么防**
**对"否定判断"要格外警惕**：`!x`、`if (!arr.length)`、`if (!obj)`。
先问一句"x 的所有可能取值是什么，falsy 包括哪些"。
更好的做法是**写正向判断**（`isPlaceholder(...)`），把意图写进函数名，
让"什么算占位符"变成一处可读、可测的定义。

### F-08 · 占位符豁免规则漏了「你的名字」——列举式永远会漏

**症状**
`gate.mjs` 的 `history-secrets` 门用来扫历史里的本机路径。
为了不误报文档里"这里会有一个路径"的写法，它加了占位符豁免：

```js
const PLACEHOLDER_SEGMENTS = /^(xxx+|user(name)?|用户名|你的用户名|...)$/i;
```

结果文档里写 `C:\Users\你的名字\...` 时，**仍然被判成真实泄漏**，门禁变红。

**根因**
豁免用的是**黑名单式的穷举**：把所有能想到的占位词列出来。
但中文里能表达"你的名字"的写法太多了——`你的名字`、`你的用户名`、`你的账户名`、
`名字`、`用户名`、`账户名`……列不全。

穷举法的本质缺陷：**你能想到的写法 ≠ 用户会写的写法**。

**为什么测试没抓到**
测试用的占位符是 `xxx`（英文），因为写测试的人脑子里是英文习惯。
**测试用例的作者和规则作者是同一个人，有相同的盲区。**

这是"自测"的固有局限：如果你没想到某个情况，你也不会想到为它写测试。

**怎么修的**
两个方向一起做：

1. **扩充**：把 `名字`、`你的名字`、`账户名`、`your[-_ ]?(name|username)`、
   `example`、`placeholder`、`<...>`、`...` 都加进去
2. **兜底**：加 `stripWrapping()` 先剥掉包裹符号（反引号、引号、括号、尖括号），
   再判断——因为文档里占位符常常被引号包着

**以后怎么防**
**黑名单永远不完整，所以要么用白名单，要么加兜底逻辑。**
具体到这条：与其列举所有可能的占位词，不如换个思路——
"如果路径最后一段明显不像真实用户名（含中文、含尖括号、含省略号），就算占位"。

另外，**规则和测试要由不同的人写**，否则盲区会重叠。本次就是让 release-engineer
（另一个 Agent）去测包工头写的规则，才发现了这个漏。

### F-09 · 测试夹具写错，伪装成「修复失败」

**症状**
修好一个制表符（`\t`）相关的问题后，回归测试**仍然是红的**。
于是判断"修复没生效"，回头又改了一遍代码——其实代码是对的，是测试写错了。

具体地：测试里为了构造"包含制表符的字符串"，写成了：

```js
const sample = "\t" + "payload";   // 期望一个制表符
```

但在多层转义（模板字符串里再套 shell 命令）之后，实际传进去的是**反斜杠 + t 两个字符**，
不是制表符。测试在验证一个根本不存在的场景，自然永远失败。

**根因**
**转义层级太多**。从 JS 源码 → 模板字符串 → shell 命令 → 被调用的脚本，
每一层都要处理转义。每多一层，写对 `\t` 的难度就翻一倍，
而且**写错了不会报错**——它只是一个普通的反斜杠加 t，语法完全合法。

**为什么测试没抓到**
这次不是"测试没覆盖"，而是**测试本身是错的**，
而且它错得很像"正确的失败"——你期望它红的时候它红了，看起来像在正常工作。

最危险的地方：**一个错误的测试会给你错误的方向**。
你会去改本来正确的代码，越改越乱。

**怎么修的**
不再在多层转义里手写控制字符，改成显式构造：

```js
const TAB = String.fromCharCode(9);   // 不依赖任何层级的转义
const sample = TAB + "payload";
```

并且在断言失败时**把实际字节打印出来**（`JSON.stringify(sample)` 或 hex），
一眼就能看出拿到的是 `"\t"`（真制表符）还是 `"\\t"`（两个字符）。

**以后怎么防**
1. 涉及控制字符/特殊字符的测试，**用 `String.fromCharCode` / `Buffer.from([...])` 构造**，
   不要依赖字面量转义
2. 断言失败信息里**永远打印实际值**（`assert.equal(actual, expected, \`实际: ${JSON.stringify(actual)}\`)`），
   否则你分不清"代码错"还是"夹具错"
3. 看到一个"意料之中的失败"时，先怀疑夹具，再怀疑代码

### F-10 · `Cache-Control: max-age=600` 让部署验证误判

**症状**
代码改好、workflow 绿了、部署成功。打开浏览器验证——**看到的还是旧版**。
于是判断"部署没生效"，重新触发 workflow、翻日志、查 artifact，折腾了 20 分钟。
最后发现：部署确实成功了，是浏览器用了缓存。

**根因**
GitHub Pages 返回 `Cache-Control: max-age=600`，即 **10 分钟**。
在这个窗口内，浏览器（包括自动化测试用的浏览器）会直接返回本地缓存的 `app.mjs`，
根本不发请求。

**为什么测试没抓到**
因为**测试代码本身也在缓存**。
用 Playwright 写"打开页面、检查某个元素存在"的测试时，
如果浏览器复用了缓存的旧 JS，测试会诚实地报告"元素不存在"——
它没说谎，它只是看的是一个旧世界。

而且 `page.goto(url, { cacheBypass: true })` 这类写法**在 Playwright 里并不生效**
（没有这个选项），容易给人"我已经绕过缓存了"的错觉。

**怎么修的**
用 CDP 真正清缓存：

```js
const client = await page.context().newCDPSession(page);
await client.send('Network.enable');
await client.send('Network.clearBrowserCache');
await client.send('Network.setCacheDisabled', { cacheDisabled: true });
await page.goto(url);
```

同时，**用字节哈希代替"看起来对不对"**——拉取线上文件算 SHA-256，
与仓库 blob 比对，缓存与否一目了然。

**以后怎么防**
1. 凡是"验证线上是否更新"，**一律用字节哈希**，不要用肉眼或"元素在不在"
2. 自动化验证前**显式清缓存**（CDP，不是 `cacheBypass` 选项）
3. 给用户的提示写清楚：看到旧界面先 **Ctrl+F5 / Cmd+Shift+R**，别急着报 bug
4. 发布流程里留出 10 分钟窗口的预期，别把缓存造成的延迟当成部署失败

## 归纳：这些坑的共同结构

10 条里有 **7 条**属于"测试全绿但仍然会炸"。它们的失败模式高度相似：

| 类型 | 涉及条目 | 特征 |
|---|---|---|
| **假通过** | F-01, F-02, F-03 | 检查器/测试本身失效，却输出绿色 |
| **环境差异** | F-04, F-05, F-10 | 测试环境比真实环境宽松 |
| **同源自测盲区** | F-08, F-09 | 规则作者和测试作者是同一个人/同一个思路 |
| **语义伪装成显示** | F-06, F-07 | 代码不报错，只是安静地做错事 |

### 四条可执行的防呆原则

1. **每个检查器都要有"故意绕过"用例**
   只测正常输入的检查器 = 安慰剂。F-01、F-02 都是这条。

2. **`catch {}` 后面不许接 `pass: true`**
   出错就是失败，别把"读失败"和"确认没有"合并。F-02 的根源。

3. **指标要选对：`todo` 和 `fail` 同等重要**
   `fail 0` 可以撒谎，因为 `todo` 不在统计里。F-03。

4. **验证要用字节，不要用观感**
   哈希能证明的事，别靠"页面能打开"。F-04、F-10。

### 最该记住的一句

> **这 10 条里，没有一条是"代码写错了"这么简单。**
> 全都是"我们以为验证过了，但其实没有"。
