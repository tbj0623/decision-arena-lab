## 坑 1：越界临界点被"贴边判断"遮蔽

### 现象
某因素的临界点算出来是 `t* = -0.0526`（负数，意为"即使把这个因素的权重压到 0 也不会翻转"），
但界面显示的是：

> 临界点正好落在 0 或 1 的边界上，在实际可调的权重范围内没有真正的翻盘空间。

用户会理解成"差一点点就能翻"，**实际是永远翻不了**。两种完全不同的语义被同一句话糊住了。

### 根因
`findFlipThresholds` 里的判断顺序写反了：

```js
// 错误顺序
if (tStar <= EPS || tStar >= 1 - EPS) { return BOUNDARY }   // 先判贴边
if (tStar < 0 || tStar > 1)           { return OUT_OF_RANGE } // 后判越界 → 永远到不了
```

`tStar = -0.0526` 满足 `<= EPS`，所以先被 `BOUNDARY` 抓走，`OUT_OF_RANGE` 分支成了**死代码**。

### 怎么发现
**两个成员各自独立发现的**：
1. Lead 在跑第一版算法 sanity check 时打印了所有阈值，看到 `code: BOUNDARY` 但 `t*` 是负数，觉得不对。
2. product-owner 在写用户旅程时，用脚本实算 J5 场景，同样看到负数 t\* 被标成 BOUNDARY，把它立成了验收项 B-15。

### 怎么修
把越界判断**提到**贴边判断之前：

```js
if (tStar < 0 || tStar > 1)           { return OUT_OF_RANGE }   // 先判越界
if (tStar <= EPS || tStar >= 1 - EPS) { return BOUNDARY }       // 再判贴边
```

### 以后怎么防
- **判断有重叠条件的 if 链，先把最严格的边界写出来**，或者干脆把条件写成互斥的。
- 给每个 `code` 分支都写一条**能真正进入该分支**的测试。本项目后来发现 `AT_THRESHOLD` 分支
  在测试里也是死代码（从没被执行过），同一个毛病犯了两次。
- **看数值不要只看标签**。如果 `code` 说"边界"但数值是 `-0.05`，这种矛盾必须人工捕捉。

来源：内部缺陷记录 B-04、`tests/core/FINDINGS.md` F-02

## 坑 2：四舍五入后，贡献列相加 ≠ 合计

### 现象
拆解表里，四个因素的"对差距的贡献"显示为：

```
+14.3   -11.4   0.0   +4.3
```

用户拿计算器一加：`14.3 - 11.4 + 0 + 4.3 = 7.2`。
但表底下的合计写的是 **+7.1**。

差 0.1。用户的结论只有一个：**这工具算错了**。

### 根因
真实值是 `14.2857 / -11.4286 / 0 / 4.2857`，总和 `7.1428`。
每一项**独立**四舍五入到 1 位：
- `14.2857 → 14.3`（进 0.0143）
- `-11.4286 → -11.4`（进 0.0286）
- `4.2857 → 4.3`（进 0.0143）

误差累计 `+0.0572`，把 `7.1428` 推到了 `7.2000`。而合计是拿原始值 `7.1428` 直接舍入成 `7.1`。

**两个不同的舍入路径，结果必然可能不一致。**

### 怎么发现
product-owner 在写用户旅程时，用脚本核对"贡献相加是否等于差值"，发现 J1 对不上。
Lead 用 `node -e` 复现确认：

```
contribution deltas 1dp: 14.3, -11.4, 0, 4.3
sum of 1dp contributions = 7.2
displayed diff           = 7.1
ROUNDING MISMATCH? true
```

### 怎么修
实现 `round1SummingTo(values, target)`：先各自舍入，算出差额，然后**每次把误差最小的那一项挪 0.1**，
直到加总恰好等于 `target` 的舍入值。

```js
let steps = Math.round((target1 - out.reduce((a,b)=>a+b,0)) * 10);
while (steps !== 0 && guard < values.length * 4) {
  // 找"挪一格之后误差增加最少"的那一项
  const dir = steps > 0 ? 1 : -1;
  ... out[bestIdx] += dir * 0.1; steps -= dir;
}
```

**验证**：5000 组随机数据压力测试 → **0 次失配**，单项最大偏差 `0.083`（小于一个显示单位）。

### 以后怎么防
- 任何"分项 + 合计"的界面，都要断言 `Σround(x_i) === round(Σx_i)`。
- 不要让用户用显示值做二次计算却得到不同答案 —— 这是最伤信任的一类"假 bug"。
- 在界面上加一句脚注说明"显示值经过取整分配"，让用户知道你没有藏东西。

来源：内部缺陷记录 B-05、`tests/qa/scenarios.test.mjs` 里的「取整一致性」测试

## 坑 3：测试断言的**前提**是错的（最有教育意义的一条）

### 现象
一条测试写着：

> 主导因素压倒弱因素：改主导因素的权重能翻盘，改弱因素翻不动

夹具：`d1 w=60 (A=10,B=1)`，`d2/d3/d4 w=10 (A=1,B=10)`。
断言：`d2` 的 `feasible === false`，理由"10 权重翻不动 60 权重"。

跑起来 **失败**，实际 `feasible === true`。

### 根因
**不是代码 bug，是人的直觉错误。**

解析解：
```
dOthers  = (60×9 + 10×(-9) + 10×(-9)) / 80 = 4.5
denom    = dk - dOthers = -9 - 4.5 = -13.5
t*       = -dOthers / denom = -4.5 / -13.5 = 1/3
```
`t* = 1/3 ∈ (0,1)` → **完全可行**。

机制不是"比谁权重大"，而是：**把权重占比 t 给目标因素，剩余 (1−t) 按原比例分给其他因素**。
d2 拿到 1/3 的总权重时，它 9 分的评分差足以抵消 d1 的优势。

代回验证：`projectAtShare(d2, 1/3)` → `A = 55.0000000000, B = 55.0000000000, diff = 1.4e-14`。
两侧符号 `+1` / `-1`，确实翻转。

### 怎么发现
Lead 复核失败测试时，没有直接说"改代码"，而是先手算解析解，发现代码是对的、测试是错的。

### 怎么修
**两个都做**（而不是简单删掉断言）：
1. 原测试改成 `feasible === true`，把 `dk/dOthers/t*` 的推导写进注释。
2. **另外新增**一个真正翻不动的用例：`d2 {A:5,B:4}`（与 d1 同向）→ `t* = 9/7 ≈ 1.2857 > 1` → `OUT_OF_RANGE`，
   且 `t=0` / `t=1` 两端都仍 A 领先。

### 以后怎么防
- **测试失败时，第一反应不能是"改代码让它绿"**。先问：断言的前提对吗？
- 任何涉及数学的断言，把推导过程写进注释或断言消息里。这样下一个人不用重新推。
- **不要用"数值大小直觉"替代解析推导**。这个坑的本质就是"60 比 10 大所以 10 翻不动"。
- 保留这个失败案例本身 —— 它比一条通过的测试更有价值。

来源：`../tests/core/FINDINGS.md`「复核过程中确认"不是 bug"的三处直觉陷阱」

## 坑 4：`node --test tests/` 在 Node 24 上根本跑不起来

### 现象
```
$ node --test tests/
Error: Cannot find module '...\tests\core'
code: 'MODULE_NOT_FOUND'
ℹ tests 1 / pass 0 / fail 1
```

一个**看起来像测试失败**的输出，实际是**命令用法错了**。

### 根因
Node 24 的 `node --test` 把参数当成 **模块/文件路径**去加载，而不是"目录下所有测试"。
传目录 → 尝试 `import('tests/core')` → 找不到模块。

### 怎么发现
CI 配置里写了 `node --test tests/`，本地跑发现失败。logic-engineer 逐一测试了 6 种写法：

| 写法 | 结果 |
|---|---|
| `tests` / `tests/` / `tests/core` / `tests/core/` | ❌ 全部 MODULE_NOT_FOUND |
| `tests/core/*.test.mjs` | ✅ |
| `node --test`（无参数） | ✅ 自动发现 `**/*.test.mjs` |

### 怎么修
- `README.md` 改成 `node --test`
- `.github/workflows/pages.yml` 改成 `node --test`
- README 里加了一句说明，解释为什么不用目录参数

### 以后怎么防
- **CI 里写的每一条命令，必须在本地原样跑过一遍**。这条命令当时如果直接进 CI，
  第一次发布会是红的，然后你会花时间怀疑代码。
- 报错信息里的 `MODULE_NOT_FOUND` 指向一个**目录**时，先怀疑命令用法而不是代码。
- 版本升级会改行为。`node --test` 的参数语义在 Node 20 → 24 之间变过。

来源：`../tests/core/README.md`（含 6 种写法的对照表）、`.github/workflows/pages.yml`

## 坑 5：枚举的第三种取值，被两处 UI 都当成二元处理

### 现象
当用户把权重拖到**恰好打平**的位置时，界面输出：

> 最容易被撬动的是「k」：把它的权重占比从 33.3% **降低**到 33.3%，两边就会打平；再往下就翻过来了。

"从 33.3% 降低到 33.3%" —— 自相矛盾，而且只描述了"往下"一个方向，实际上往哪边拨都会翻。

### 根因
`findFlipThresholds` 的 `direction` 字段有三个值：`'increase' | 'decrease' | 'hold'`。
`'hold'` 表示"当前占比恰好就在临界点上"。

但两个消费方都写成了二元判断：

```js
// app.mjs
flip.direction === 'increase' ? '提高' : '降低'      // 'hold' 掉进 '降低'
// narrative.mjs
`从现在的 ${pct(current)} 挪到 ${pct(threshold)}`     // 两个数一样
```

数学层是对的，**错的是 UI 把它硬塞进二元分支**。

### 怎么发现
logic-engineer 在写 FINDINGS 时，逐个检查了 `direction` 的消费点，构造了真打平夹具
（`46.66 / 46.66`）复现出来。

### 怎么修
**选择改 UI 而不改 core**，理由：`'hold'` 这个取值本身是**合理**的
（它如实表达了"当前位置就在临界点上"），错的是消费方。改 core 的影响面更大。

```js
if (flip.direction === 'hold') {
  return `「${label}」现在的权重占比 ${cur} 恰好就是打平点。此刻两边分数相同——往任一方向拨动都会立刻偏向一方。`;
}
```

同时在阈值列表里，`hold` 状态的数字显示为 `已打平` 而不是重复的百分比。

### 以后怎么防
- **新增枚举值时，grep 所有消费点**。`direction` 只在两处被读，但两处都错了。
- 给枚举加**封闭值域断言**：`assert.ok(['increase','decrease','hold'].includes(t.direction))`。
  这样以后加新值而 UI 没接，测试会立刻报错。
- 三元表达式 `a === 'x' ? A : B` 是二元假设的典型信号。枚举有 3 个值时不要这么写。

来源：`../tests/core/FINDINGS.md` F-01

## 坑 6：`work/` 被 git 跟踪了，再公开就是泄露内部过程稿

### 现象
准备建公开仓库前，检查 `git ls-files` 发现：

```
work/product/ACCEPTANCE_CHECKLIST.md
work/product/PRD_FREEZE.md
work/product/SCOPE_CUTS.md
work/product/USER_JOURNEYS.md
work/product/verify-journeys.mjs
work/ux/after-360-full.png
```

`work/` 是成员的过程稿目录，本来约定"不公开"。但它被 `git add -A` 顺手加进去了。
`dist/`（含发行 ZIP 和 SHA）也一起被跟踪了。

### 根因
`.gitignore` 里只写了 `work/**/tmp/`，意思是"排除 work 下的临时子目录"，
而不是"排除整个 work"。**规则写得太窄，而 `git add -A` 太宽。**

而且：**`.gitignore` 对已经被跟踪的文件无效**。一旦 `git add` 过，加规则也不会自动移除。

### 怎么发现
Lead 在写发布预检时手动跑了 `git ls-files` 并逐个审视 —— 不是靠某条自动化规则。

### 怎么修
```bash
git rm -r --cached work      # 从索引移除，磁盘文件保留
git rm -r --cached dist
```
然后 `.gitignore` 改成整目录排除：
```
work/
reports/
dist/
```
最后把**确实要公开的成果**复制到 `docs/product/` 下（PRD、旅程、验收清单），
让它们以"审定过的文档"身份进入公开仓库，而不是以"过程稿"身份泄露。

### 以后怎么防
- **发布前必须人工过一遍 `git ls-files`**，不能只看 `.gitignore` 写了什么。
- `.gitignore` 用整目录排除（`work/`），不要用"排除子目录"（`work/**/tmp/`）—— 后者几乎总是漏。
- 建立"公开面 / 内部面"的明确划分，并且**在项目第一天就建好**，不要等到发布前才想起。
- `git rm --cached` 只影响后续提交；**已经推送的历史仍然包含这些文件**。
  本次很幸运是在推送前发现的。如果已经推送过，需要 `git filter-repo` 重写历史（并视为一次事故）。

来源：`../.gitignore`、`../README.md` 项目结构说明

## 一条元教训

上面 6 个坑里，**没有一个是"算法写错了"**。

- 坑 1 是 **if 判断顺序**
- 坑 2 是 **显示层取整**
- 坑 3 是 **人的直觉**
- 坑 4 是 **命令用法**
- 坑 5 是 **枚举消费点漏了第三个值**
- 坑 6 是 **工程卫生**

也就是说：多智能体协作里，真正消耗时间的**不是"想不出算法"，而是"集成时的边界"**。
这就解释了为什么 `FILE_OWNERSHIP.md`、`QUALITY_GATES.md` 这些"流程文件"比"多派几个 Agent"更重要。
