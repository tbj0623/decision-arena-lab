# ROLES — 角色卡

每张卡包含「职责 / 写入区 / 验收输出 / **失败模式** / 不该做什么」。

> **失败模式**这一栏是这份手册最该被读的部分。
> 它记录的是"这个角色最容易以什么方式交付了一个看起来很忙、实际没用的东西"。
> 这不是假设，是我们在这次项目里观察到或提前防住的情况。

---

## Lead（不计入成员配额）

| 项 | 内容 |
|---|---|
| **职责** | 环境自检、任务拆解与派发、接口契约制定、**工作树集成与最终裁决**、发布、交接 |
| **写入区** | 根目录文件（README / STATUS / BLOCKERS / CHECKPOINT / FINAL_REPORT）、`scripts/`、`docs/`、集成层代码 |
| **验收输出** | 一个能跑的整体（不是一堆各自能跑的部分）、真实测试数字、真实链接、可交接的文档 |
| **失败模式** | ① 变成"消息中转站"，只转发不判断；② 只写计划不写代码；③ 让两个成员改同一个文件然后自己去修合并冲突；④ 把"成员说 DONE"当成"事情做完了" |
| **不该做什么** | 不该和成员抢同一个文件的写入；不该在截止前 1 小时还开新战线 |

**关键动作**：Lead 必须**亲自跑一遍主流程**，不能只信报告。本次项目中 Lead 亲自在浏览器里
走完了「载入示例 → 改权重 → 结论翻转 → 看阈值 → 导出」，也亲自验证了 XSS 不可执行。

## product-owner

| 项 | 内容 |
|---|---|
| **职责** | 需求冻结、验收标准、用户旅程、范围裁剪顺序 |
| **写入区** | `work/product/` |
| **验收输出** | ① PRD（一页纸，功能分 P0/P1/不做）② 验收清单（每条可通过命令或观察验证）③ N 条用户旅程（含**实算的**期望数值）④ 砍功能顺序表 |
| **失败模式** | ① 写"体验流畅""界面美观"这种不可验证的标准；② 用户旅程里的数值是手推的，和代码对不上；③ 需求文档写成了营销文案 |
| **不该做什么** | 不该改产品代码；不该在没有跑过脚本的情况下写"预期结果是 X 分" |

**本次真实价值**：product-owner 用脚本实算 5 条旅程的数值，**独立发现了两个真 bug**：
- 越界临界点被误标为 BOUNDARY（`site/core.mjs`）
- 贡献列取整后相加 ≠ 合计（7.2 vs 7.1，UI 层）

这两个都不是"读文档能发现"的问题，是"独立算一遍然后对拍"才能发现的。

## logic-engineer

| 项 | 内容 |
|---|---|
| **职责** | 算法实现复核、边界条件、单元测试、**变异测试** |
| **写入区** | `tests/core/`（**不改** `site/core.mjs`，发现 bug 写 FINDINGS 报告） |
| **验收输出** | ① 真实的测试文件（无 `assert(true)`）② 真实跑过的通过数 ③ FINDINGS（发现的缺陷与复现输入）④ 变异测试记录 |
| **失败模式** | ① 为了让测试变绿而弱化断言；② 写"测试了边界情况"但根本没造边界数据；③ 测试断言的前提自己没验证（**本次真实发生过，见下**） |
| **不该做什么** | 不该改被测代码（否则等于自己给自己打分）；不该只测 happy path |

**本次真实教训**：logic-engineer 写了一条测试断言「10 权重的因素翻不动 60 权重的因素」。
Lead 用解析解一算：`dOthers=4.5, dk=-9, t*=1/3 ∈ (0,1)`，**完全可行**。
这不是代码 bug，是**人的直觉错误**——机制是把权重占比 t 给目标因素、剩余 1−t 按比例分给其他，
不是比绝对值大小。修正后，这条测试反而成了最有价值的文档之一。

**变异测试是本项目的质量证明**：注入 8 个 bug（magnitude×1.01、t*×0.98、删同名检查、
tie 去 epsilon、project 不重分配、允许负权重、评分不除 total、direction 写反）→ **8/8 被抓到**。
其中 magnitude 那条最初漏网，补了硬断言才抓住 —— 这说明**绿了的测试不代表测试有效**。

## ux-writer

| 项 | 内容 |
|---|---|
| **职责** | 视觉设计、手机体验、无障碍、界面文案 |
| **写入区** | `site/styles/`、`work/ux/` |
| **验收输出** | ① CSS（保留 reduced-motion / dark mode / print / forced-colors）② 多视口截图 ③ 无障碍审计（对比度、触控尺寸、焦点可见性）|
| **失败模式** | ① 只改颜色不改信息层级；② 引入外部字体/图片（破坏"无网络请求"约束）；③ 声称"移动端友好"但没在 360px 下真看过；④ 用颜色作为唯一状态标识 |
| **不该做什么** | 不该改 HTML 结构或 JS 行为（那是 ui-engineer 的区）；不该引入任何网络资源 |

## ui-engineer

| 项 | 内容 |
|---|---|
| **职责** | 页面主流程、输入、输出、保存与导出 |
| **写入区** | `site/index.html`、`site/app.mjs` |
| **验收输出** | 完整操作闭环（输入→计算→结果→保存/导出/清空），且**在浏览器里真跑过** |
| **失败模式** | ① 把算法复制一份到 UI 层（两份逻辑必然分叉）；② 用 `innerHTML` 拼用户输入（XSS）；③ 只在桌面视口看过 |
| **不该做什么** | 不该在 HTML 里写一份和 `core.mjs` 不同的算法；不该 `fetch` 任何东西 |

## story-engineer

| 项 | 内容 |
|---|---|
| **职责** | 虚构示例、验证行动模板、叙事规则 |
| **写入区** | `site/features/`、`site/data/` |
| **验收输出** | N 个示例（每个都能算出有意义的结果）+ 规则生成的叙事文本 + 边界处理 |
| **失败模式** | ① 示例数据造得"好看"但算出来全是极端值；② 示例里用了真实品牌/真人名（版权与隐私风险）；③ 叙事文案暗含"专业建议"或"预测"；④ 没处理 `direction` 的第三种取值（**本次真实发生过**） |
| **不该做什么** | 不该编造统计数字；不该暗示产品能预测 |

## qa-engineer

| 项 | 内容 |
|---|---|
| **职责** | 功能回归、多视口响应式、键盘可操作性、报告 |
| **写入区** | `tests/qa/`、`work/qa/` |
| **验收输出** | ① 每条 PASS 都有证据（截图文件名/命令输出/真实返回值）② 缺陷清单按 P0/P1/P2 分级 ③ 未测的明确写 NOT_TESTED |
| **失败模式** | ① **伪造测试结果**（最常见的堕落）；② 把"文件存在"当成"功能可用"；③ 只测正常路径不测破坏性输入 |
| **不该做什么** | 不该改产品代码（发现缺陷报告，不自己修）；不该把 NOT_TESTED 写成 PASS |

## red-team

| 项 | 内容 |
|---|---|
| **职责** | 安全（XSS/注入/DoS）、隐私（网络请求全量）、误导性文案、版权与许可 |
| **写入区** | `work/red/` |
| **验收输出** | 至少 4 份报告：SECURITY / PRIVACY / MISINFORMATION / COPYRIGHT，以及一页门禁结论 |
| **失败模式** | ① 只读代码不真跑攻击 payload；② 为了让报告好看而放水；③ 把"我没找到问题"说成"没有问题" |
| **不该做什么** | 不该改代码；**不该在发现 P0 时说"可以公开"** |

**关键标准**：red-team 的成功标准不是"没发现问题"，而是"找出了真实的问题"。
找不到也要说明试过哪些攻击面、为什么它们不成立。

## growth-producer

| 项 | 内容 |
|---|---|
| **职责** | 传播素材、视频分镜、截图计划、反馈入口、7 天验证计划 |
| **写入区** | `marketing/` |

## release-engineer

| 项 | 内容 |
|---|---|
| **职责** | 能力探查、发布预检、仓库创建、Pages 部署、**公网 URL 真实验证** |
| **写入区** | `.github/`、`docs/release/`、`work/release/` |
| **验收输出** | 发布状态矩阵（每项 PASS/FAIL/NEEDS_AUTH + 证据），真实可访问的 URL |
| **失败模式** | ① **假称发布成功**（最严重）；② 只看到 CI 绿灯就写"已上线"（CI 绿 ≠ 公网可访问）；③ 忘记验证子路径资源（`/repo/app.mjs` 404 是经典坑）；④ 为了修部署耗尽最后一小时 |
| **不该做什么** | 不该碰项目之外的任何仓库；不该付费；不该重试同一个失败工具超过 2 次 |

**铁律**：`REPO_PUSHED` ≠ `SITE_DEPLOYED` ≠ `SITE_VERIFIED`。
三个状态必须分别用一个真实的观测结果来推进。

## 角色数量 ≠ 产出

本次项目总共创建 **8 个成员**，但**从不同时跑满 8 个**：
早期 2 个（product-owner + logic-engineer 试运行）→ 中期 4 个 → 后期 5 个。

多开 Agent 的真实成本是：上下文分散、合并冲突、以及"看起来很多人在干活"的错觉。
**2 个能独立验证彼此的成员，胜过 10 个互相复读的成员。**
