## 二、缺陷台账（V9 阶段，截至 v9.34）

### 2.0 这个数字怎么读（先看这段，否则会数错）

原报告写「修掉的缺陷：42 个」，但那个 42 的算术是
**11（阻断）+ 9（严重）+ 17（一般）+ 5（自引入）= 42** ——
而「一般级」那一节后来被追加到了 **27 条**（v9.26–v9.32 陆续补进来），标题却没改。
所以 42 与清单**对不上账**。本轮把这个账摊平：

| 类别 | 原报告声称 | 本轮逐条清点 | 说明 |
|---|---|---|---|
| 阻断级 | 11 | **11** | 一致 |
| 严重级 | 9 | **9** | 一致（原编号 7–15 与阻断级编号重复，本表重编为 S01–S09） |
| 一般级 | 17 | **27** | 标题未随条目追加而更新（多出 10 条） |
| 自引入 | 5 | **5** | 一致（R01–R05） |
| **合计条目** | 42 | **52** | 11 + 9 + 27 + 5 |
| **去重后唯一缺陷** | — | **48** | 52 − 4（见下） |

**判定为重复/同源的 4 条**（同一次提交、同一个根因，拆成两行会让总数虚高）：

| 行 | 与谁同源 | 理由 |
|---|---|---|
| `B09` 输入 `11` 污染分数 | `B01`（评分「边打边提交」） | 同一根因「提交时机」，两轮修复；`R03` 是它的第三次记录 |
| `G22` 首屏「差 0.0 分」却没打平 | `B08`（UI 说打平但分数不相等） | 同一根因「差值取整与分数取整不同源」，同在 `ff7624a` 修复，覆盖首屏与结果卡两个可见面 |
| `G25` 我自己引入的 CLS 回归 | `R04` | 同一件事在两节各记一次 |
| `R03` 「非法值不写入」只堵一半 | `B01` / `B09` | 同上，第三次记录同一根因 |

> **结论**：不再使用「42」这个数字。V9 清单的唯一缺陷数是 **48**。
> 这个数可以逐条核对：下面四张表，行数分别是 11 / 9 / 27 / 5。

### 7.3 推送：复用 credential helper，token 不进 argv

```bash
node scripts/push.mjs --check      # 只做本地预检，不联网、不推送
node scripts/push.mjs --dry-run    # 连远端演练，不写入
node scripts/push.mjs              # 推当前分支
node scripts/push.mjs --allow-main # 发布时才允许推受保护分支 main
```

- **凭据全程不进命令行**：脚本只把 `origin` 和 `HEAD:refs/heads/<branch>` 交给 `git push`，
  认证由 credential helper（`gh auth git-credential`）在管道里完成。
- **默认拒绝直推 `main`**，要显式 `--allow-main`。
- **禁用 `--force` / `--force-with-lease`**：非快进会被拒绝（退出码 5）。
- **已弃用**：用 `gh auth token` 取明文令牌、拼成带 userinfo 的远程 URL 再 `git push`。
  弃用原因：令牌会进入**子进程 argv**（同机其他进程可读），也会被 git 的错误信息带出去。
  这条旧做法一度被写成本项目的"当前方案"，是错的；现在归入 `V10-01`。
- 退出码：`0` 成功 / `2` 用法或配置不匹配 / `3` 缺 credential helper /
  `4` 网络重试耗尽 / `5` 非快进被拒 / `6` 认证失败 / `7` 远端 SHA 不一致。

推完断言 `远端 tree === 本地 HEAD tree`）。它不在版本控制里，属于本机工具。

## 九、这轮学到的 13 条

1. **`undefined` 为假，会让"条件不满足"和"字段不存在"长得一模一样。**
   `projectAtShare` 没有 `tie` 字段，用 `projected.tie` 做判据恒假。

2. **CSS 变量未定义时整条声明失效，而对比度检测会给假阳性。**
   检测脚本找不到背景就回退白色页面底，算出 17.47:1 "很够"。

3. **`break-inside: avoid` 不是强制约束，是"尽量"。**

4. **`base_tree` 的语义是"叠加"，不是"快照"。** 用它推删除永远推不掉，且不报错。

5. **测试可以永远不会失败。** 断言必须限定在**该检查的区块**内，并且要有负向验证。

6. **一个评分错误可以悄悄支撑一个教学结论。**

7. **一条话说满了，会主动帮倒忙。** "全票通过"恰恰是评分填反的典型指纹。

8. **"试算"和"真改"必须分清。** 演示滑杆改的是 `t`（投影），按钮改的是 `state`（真数据）。

9. **一个修复可以制造新的矛盾。** 审计的价值是找所有人的错，包括自己。

10. **「非法值不写入」是必要条件，不是充分条件。** 根因是"何时提交"，不是"什么算合法"。

11. **改完一个指标要立刻复测。** 修复本身可以变成回归（CLS 0.00006 → 0.034）。

12. **一行结构改动胜过一堆措辞修补。** 28 个控件同名的根因是 `<li>` 没有分组边界。

13. **最危险的不是算错，是"改完数据后报假成功"。**
    「跳到精确临界点」在权重被上限截断时仍然说"两边分数相同" ——
    用户会截图发给朋友说"我用工具算过了"。**免责声明救不了一句假断言。**

## 十、验证纪律（这轮反复救命的几条）

- **复现先于修复**：每个缺陷都先在浏览器/脚本里复现，再动手。
- **负向验证**：每道防线都要证明"改坏它会变红"。
  例：id 契约测试改坏 `#factor-list` → 红并指出缺失 id；
  分享精度测试去掉精度参数 → 测试变红。
- **对源码做文本断言，第一步必须剥注释**（否则注释里的示例代码会让断言假过）。
- **部署验证必须用 `no-cache` 或 CDP 清缓存**（Pages 有 `max-age=600`，会伪造"没生效"）。
- **审计期间 `site/` 会被并发修改**，所以要用字节冻结快照，并在运行前后核对 sha256。
- **区分"显示同分"和"精确同分"**：`|Δ| < 1e-9` 才允许说"分数完全相同"；
  只是保留 1 位小数后相同，必须写"显示为相同分数（四舍五入），原始计算存在细微差异"。
- **写文档时，任何"现在可执行"的断言都要当场跑一遍**。本文件里
  `git rev-list --count HEAD = 54`、`revert` 退出码 0、`253 pass` 都是本轮实跑的结果。
