## 一、反馈入口：只用 GitHub Issues

### 为什么不用表单、不用问卷、不收集邮箱

这个产品全部代码里没有 `fetch`/`XHR`/`WebSocket`/`localStorage`，`node scripts/check-no-network.mjs` 会逐文件扫出来。如果为了"收集反馈"在页面上挂一个第三方表单，等于亲手破坏了它最核心的卖点。所以：**反馈统一走 GitHub Issues，工具本身永远不加任何埋点。**

### 需要创建的标签（Labels）

| 标签 | 颜色建议 | 含义 |
|---|---|---|
| `feedback` | `#0e8a16` | 所有用户反馈的总入口 |
| `bug` | `#d73a4a` | 能复现的功能错误 |
| `copy` | `#fbca04` | 文案歧义、误导性表述 |
| `math` | `#1d76db` | 算法/数值疑义（会要求给出手算过程） |
| `ux` | `#c5def5` | 交互与可读性 |
| `wontfix-by-design` | `#cccccc` | 属于明确的设计取舍，附上 LIMITATIONS 链接 |
| `needs-info` | `#e99695` | 信息不足，等待补充 |

### Issue 模板（`.github/ISSUE_TEMPLATE/feedback.yml`）

以下是建议提交给 release-engineer 落地的模板内容。核心原则：**只要可复现的信息，不要身份信息。**

```yaml
name: 反馈 / Feedback
description: 报告一个问题、一处看不懂的文案，或一个数值疑义。请不要填写任何个人信息。
title: "[反馈] "
labels: ["feedback"]
body:
  - type: markdown
    attributes:
      value: |
        **请不要在 Issue 里填写：** 真实姓名、邮箱、电话、公司名、住址、
        真实的决策内容（尤其是涉及家人、同事、健康的细节）。

        你不需要提供任何身份信息，我们也不会问。

        如果你的例子涉及真实的人和事，请把它改写成虚构的：
        把「和某某同事」写成「和一位同事」，把具体金额改成「大约 X 千元」。

  - type: dropdown
    id: kind
    attributes:
      label: 类型
      options:
        - 数值/算法疑义（math）
        - 文案不清楚或可能误导（copy）
        - 功能不工作（bug）
        - 交互/可读性（ux）
        - 其他
    validations:
      required: true

  - type: textarea
    id: what
    attributes:
      label: 发生了什么
      description: 一句话说清你期望看到什么、实际看到什么。
      placeholder: 我期望……实际是……
    validations:
      required: true

  - type: textarea
    id: steps
    attributes:
      label: 复现步骤
      description: 从打开页面开始，一步一步写。数值问题请注明每个因素的权重和你打的分。
      placeholder: |
        1. 打开页面，点「示例」第一张卡（职业 · 换个地方，还是先待着）
        2. 把「收入确定性」权重从 4 拖到 7
        3. 结果卡显示 A 65.3 / B 66.5
    validations:
      required: true

  - type: input
    id: expected
    attributes:
      label: 你认为正确的数值或文案（可选）
      description: 如果是数值疑义，请附上你的手算过程或算式。
    validations:
      required: false

  - type: input
    id: env
    attributes:
      label: 浏览器与系统（可选）
      description: 例如 Chrome 130 / Windows 11。不建议粘贴完整 User-Agent。
    validations:
      required: false

  - type: checkboxes
    id: privacy
    attributes:
      label: 隐私自查
      options:
        - label: 我确认本 Issue 中不含真实姓名、联系方式、公司名或他人的敏感信息。
          required: true
        - label: 我理解这个工具不提供医疗、法律、财务等专业建议。
          required: true
```

### 处理约定（写给自己看的）

1. **48 小时内首次回应**，哪怕只是"收到了，正在看"。做不到就不要开这个入口。
2. 数值疑义一律先要求"权重 + 每个因素的 A/B 评分"，然后用 `node -e` 现场跑 `core.mjs` 复算，把结果贴回 Issue。**不许凭印象说"应该是对的"。**
3. 文案类反馈优先级高于功能类——这个产品最容易死的地方是被读成"预测工具"，一句歧义比一个 bug 危险。
4. 明确属于设计取舍的（例如"为什么不能同时改两个因素的权重"），标 `wontfix-by-design` 并链接 `docs/LIMITATIONS.md` 对应小节，不要含糊其辞。
5. **不主动索要**任何个人信息，包括"方便留个邮箱吗"。

### 试用记录表模板（Day 4 用）

> 5 人里只要有 **2 人以上**问出"所以它觉得我该选哪个"，说明定位没传达清楚——这不是用户的问题，是文案的问题。

### 决策阈值（**目标值，非已达成**）

| 判断 | 条件（7 天累计） | 含义 |
|---|---|---|
| **继续投入** | ≥3 条有效反馈（含至少 1 条具体改进建议）**且** 0 条"把我误导成预测工具"的反馈**且** 有 ≥1 人完整走完一次决策 | 说明有人真的用得上，值得继续 |
| **调整定位** | 出现 ≥2 条"它到底有什么用"或"这不就是算个加权平均"的反馈 | 价值点没讲清，先改文案与演示，别加功能 |
| **暂停并修** | 出现任何 1 条数值错误反馈（经复算确认） | 数学是唯一不能错的东西，先修再谈推广 |
| **停止 / 归档** | 7 天访客 < 50 **且** Issue 0 条 **且** 无一人完整走完 | 说明这个形态没有真实需求，如实记录并归档，不粉饰 |

> 阈值是**事前**定的，发布后不许因为"再等等看"而改写。要改就在 Day7 的复盘里写明"原阈值 X，实际 Y，为什么调整"。
